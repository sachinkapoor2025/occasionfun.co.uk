## 6. Technical implementation

Cursor should inspect the repository first. If no existing application
exists, choose a maintainable modern stack.

### Preferred default stack

-   Next.js with TypeScript.
-   App Router.
-   React.
-   Tailwind CSS or a similarly maintainable styling system.
-   Accessible component primitives.
-   Server-side rendering/static generation as appropriate.
-   Zod or equivalent for server-side form validation.
-   A lightweight, maintainable content structure (MD/MDX or typed
    content data) for service and policy pages.

If the existing repository already has a sound framework, preserve it
unless there is a strong technical reason to migrate.

### Architecture requirements

-   Reusable header, footer, CTA, service card, trust panel and
    document-list components.
-   Consistent design tokens.
-   Semantic HTML.
-   Accessible forms and navigation.
-   Responsive breakpoints.
-   Error and loading states.
-   Centralised site configuration for company details and contact
    placeholders.
-   No secrets in frontend code.
-   Environment variables for all service credentials.
-   Basic automated tests for critical routes and form validation.
-   Linting, formatting and type checking.
-   Build must pass without warnings that indicate broken functionality.

### AWS hosting decision: Amplify vs S3

Evaluate the actual application before choosing.

**Preferred approach: AWS Amplify Hosting** if the selected Next.js
configuration needs managed Next.js hosting, server-side rendering,
preview deployments, integrated CI/CD or a straightforward deployment
workflow. Confirm current framework/runtime support and costs before
implementation.

**Alternative: Amazon S3 + CloudFront** if the website is exported as a
fully static site and does not require server-side rendering or server
runtime features. Configure: - Private S3 origin (prefer Origin Access
Control). - CloudFront distribution. - HTTPS with AWS Certificate
Manager certificate in the required region. - Custom domain and DNS. -
Sensible cache policy and invalidation/deployment process. - Security
headers. - Access logging as appropriate.

Do not choose S3 static hosting if the implementation depends on
server-side Next.js features that static export cannot support.

**Forms and backend:** If a backend is needed, use an appropriate AWS
service such as API Gateway + Lambda, or another maintainable managed
service. Store submissions securely, validate server-side, rate-limit
and protect against spam. Send notifications through a properly
configured email service. Do not expose AWS credentials or email
provider keys in browser code.

**Infrastructure and operations:** - Separate development/staging and
production environments where practical. - Use least-privilege IAM
roles. - Store secrets in AWS Secrets Manager or an appropriate secure
configuration service. - Enable HTTPS only. - Configure DNS carefully. -
Set up monitoring and error logging without collecting unnecessary
personal data. - Document deployment, rollback and domain
configuration. - Provide an estimated monthly cost only after selecting
the architecture and checking current AWS pricing; do not invent a
guaranteed cost.

### SEO and performance

-   Unique page title and meta description per route.
-   Canonical URLs.
-   XML sitemap and robots.txt.
-   Open Graph metadata.
-   Structured data for Organisation/LocalBusiness only with verified
    fields; do not invent address, telephone or social profiles.
-   Optimised images and fonts.
-   Lazy-load non-critical media.
-   Core Web Vitals-conscious implementation.
-   Descriptive URLs and internal linking.

### Accessibility

Aim for WCAG 2.2 AA as an implementation target: - Keyboard
navigation. - Visible focus states. - Sufficient colour contrast. -
Correct heading hierarchy. - Labels and accessible error messages. - Alt
text for meaningful images. - Reduced-motion support. - No colour-only
status communication.

Do not claim formal WCAG certification or an independent accessibility
audit unless completed.

## 9. Security, privacy and operational safeguards

-   Validate all form inputs on the server.
-   Apply rate limiting and anti-spam protection.
-   Use CSRF protection where relevant to the chosen architecture.
-   Escape and safely render user-submitted content.
-   Restrict access to enquiry submissions.
